# Проверяемый маршрут Remnawave entry → exit

Прочитай этот файл целиком перед изменениями. Порядок допускает независимые
read-only проверки параллельно; изменение одного ресурса принадлежит одному
исполнителю. Коротко сообщай результаты этапов, не публикуя секреты.

## 1. Однозначные цели и исходное состояние

- Раздели management/ingress/egress IP, DNS и логические роли entry/exit.
  Сверь SSH host keys, фактический адрес сервера, ноду/UUID/профиль в панели,
  все привязанные inbounds, хосты и сквады. При несовпадении остановись.
- Проверь ОС, установленные версии Remnawave/Xray, контейнерную сеть,
  владельцев портов, IPv4/IPv6 firewall, HTTPS и ACME. Используй фактическую
  схему API/конфигурации установленной версии, не старые имена полей наугад.
- Установи, какие другие ноды/хосты используют профиль. В область изменения
  входят только явно выбранный вход, выход и их нужные связи; скрытый авто-хост
  нужно найти по связям, не по похожему имени. Не считай количество маршрутов
  или сквадов фиксированным.
- Для нового сервера сначала установи, нет ли работающей ноды под другим именем.
  Установи/зарегистрируй отсутствующую ноду обычным поддерживаемым способом,
  с ответом на self-steal-вопрос и без переустановки соседних сервисов.
  Новая инсталляция требует новых идентичностей; миграция сохраняет прежние.
- Сними baseline старого клиента, реальной текущей подписки (основной/авто),
  ожидаемых выходных IP, состояния нод и доступности API именно с панели.
  Секретные ответы API, env и docker inspect
  не печатай целиком. SSH — с проверкой ключа хоста, без отключения host checking.

## 2. Снимок, владение и план портов

До первой мутации сохрани затрагиваемые профили/связи/хосты и файлы серверов,
firewall, DNS ID и значения. На сервере: root-only каталог, файлы `0600`,
проверка читаемости/целостности и SHA-256; вне Linux — эквивалентные ACL.
Секретные снимки не должны попасть в рабочий Git или публичный журнал.
Запиши baseline, точные создаваемые объекты и hashes ожидаемого нового состояния.

Предпочтительная архитектура входа — публичные Xray inbounds на отдельных
свободных портах для добавляемых маршрутов. Занятый legacy 443 остаётся со своим
владельцем; сохраняются старые ключи, short IDs, SNI, flow и fingerprint.
Проверь порт не только в файле, но и в реальных listeners и namespace.
Делить занятый 443 через новый SNI-router можно лишь как явно согласованное
изменение архитектуры с отдельными тестами и откатом, не как скрытый шаг.

Общий профиль клонируй для целевой ноды, сохраняя остальные поля и зависимости;
новые inbound tags должны быть уникальны, ссылки routing должны соответствовать.
У выделенного профиля делай минимальное добавление и проверяй drift перед записью.
Сохраняй неизвестные поля API. Не обновляй всю систему и не перезапускай VPN
ради установки nginx/ACME; учитывай автозапуск и needrestart при установке пакетов.
При необходимом применении профиля предупреди о переподключении только цели.

Открой только выбранные frontend-порты; API разреши панели и loopback в нужных
семействах адресов, SSH оставь доступным. Закрывай публичный IPv6 API, если
нет явно разрешённой IPv6 панели. Сохрани несвязанные правила и persistency;
не очищай INPUT, DOCKER-USER или весь ruleset.

## 3. Независимый межсерверный канал

### Сначала direct

Используй отдельный backend inbound и служебную идентичность для entry→exit,
не клиентскую подписку. Сохрани существующих клиентов и backend-правила выхода.
Если источник entry стабилен, ограничь новый публичный backend этим источником,
не закрывая существующие разрешённые пути. Не публикуй backend в клиентских хостах.
Шифрование должно быть на этом участке: VLESS с проверяемым TLS либо REALITY
с соответствующей идентичностью; self-steal frontend не защищает backend сам.
Не используй skip-verify, чужие ключи или случайный SNI как замену проверке.

Из реального namespace входа проверь именно установленным Xray: handshake,
аутентификацию, запрос HTTPS с ожидаемым 204 и определение ожидаемого exit IP.
Исследуй TCP/TLS/маршрут/firewall при ошибке. Открытый порт, ping или успешный
доступ с ноутбука вместо entry недостаточны. При успехе не добавляй reverse SSH.

### Fallback: ограниченный reverse SSH

Если direct действительно не работает и обратный SSH доступен, сообщи причину
fallback. При необходимости нового доступа или расширения scope сначала
запроси его; не обходи запреты панели/администратора.

- Выход инициирует туннель к входу; remote listener на входе — только loopback
  и выбранный свободный порт, target на выходе — только конкретный backend.
  Xray входа обращается к этому listener; внешние клиентские порты не меняются.
- Для каждой пары/маршрута отдельная непривилегированная SSH-учётка или строго
  ограниченная identity; ключ генерируется на нужном сервере. Не копируй
  операторские private keys. Пинь ключ хоста, отключи пароль/interactive auth
  для этой identity, задай ограничение по source, если адрес стабилен.
- Эффективная политика разрешает только нужный remote TCP forwarding и точный
  loopback listen address/port. Запрети shell/exec/subsystem sessions, PTY,
  agent/X11, локальный/динамический forward и wildcard bind. Не меняй глобально
  политику sshd для остальных пользователей; проверь конфиг и effective Match.
- `PermitListen` ограничивает listener, но не target на машине SSH-клиента.
  Если нужен доказуемо фиксированный target, используй проверенный клиент/relay
  с такой проверкой; не объявляй это свойством одного authorized_keys-флага.
  Не отключай forwarding без разбора: нужный туннель тоже перестанет работать.
- Оформи отдельный persistent сервис с bounded reconnect/keepalive, без
  busy-loop и секретов в argv/logs. Проверь перезапуск именно этого сервиса,
  восстановление туннеля и отсутствие публичного listener/open proxy.
- Повтори через туннель аутентифицированный backend 204 + exit IP. Зафиксируй
  фактический транспорт; plain VLESS допустим только внутри проверенного
  SSH-шифрования и на loopback endpoints, не на публичном участке.

## 4. Свой сайт и сертификат

Этот раздел выполняется только при self-steal=да; он достаточен и без другого
навыка. Согласуй конкретный FQDN каждой цели, тему сайта и безопасный доступ
к DNS/сертификатам. Не используй домен автора навыка или чужой IP как default.

1. Проверь A/AAAA/CNAME и текущего владельца HTTPS. Новые записи — DNS only
   на подтверждённый ingress; конфликтующие записи меняй лишь при согласованной
   миграции, сохрани их ID/состояние. Не покупай домен автоматически.
2. Подготовь небольшой статический сайт без вымышленных отзывов, контактов или
   платежей. Переиспользуй веб-сервер либо установи минимальные пакеты без
   общего upgrade/restart VPN. Не удаляй чужой/default vhost. Проверь HTTP Host
   и webroot ACME challenge; каталог должен читаться nginx после root-only umask.
3. Для нового домена выпусти сертификат после подтверждения DNS и challenge.
   Для миграции существующего домена сначала безопасно переиспользуй действующий
   сертификат, если разрешён доступ к нему; не запускай повторный production ACME
   ради переноса. Если это невозможно, согласуй способ валидации/окно DNS,
   не подменяй сертификат самоподписанным и не меняй DNS преждевременно.
4. При переносе разрешены только выбранные live/archive/renewal lineage и его
   конкретный ACME-аккаунт. Не копируй всё хранилище, DNS API tokens и SSH-ключи.
   Передай бинарные bytes через защищённый канал stdout→stdin без вывода/диска
   оператора; на приёмнике проверь размеры, пути, типы, symlink targets, состав,
   SAN, срок, цепочку и соответствие private key до включения. Renewal не должен
   содержать непереносимые hooks/секреты; согласуй новый метод вместо копирования.
5. TLS сайта слушает только свободный loopback-порт. Проверь доступность target
   из namespace Xray: loopback контейнера и хоста могут различаться. Не меняй
   сеть работающего контейнера и не публикуй этот порт ради удобства.
6. Проверь конфиг nginx, HTTPS-содержимое, доверенную цепочку/имя, TLS 1.3 и
   ALPN h2 для всех выбранных SNI. REALITY target указывает на проверенный
   endpoint; используй поля, поддержанные установленным Xray. У миграции
   сохраняй прежние frontend-идентичности и serverNames для cached-клиентов.
7. После DNS cutover проверь readback и минимум два публичных резолвера,
   отсутствие неожиданной AAAA, challenge и внешнюю HTTPS-доступность.
   Затем staging renewal dry-run с deploy-hook; проверь поддержку
   `--no-random-sleep-on-renew` установленным certbot перед применением флага.
   Подтверди reload-hook и persistent renewal timer. При ещё старом DNS
   явно отложи dry-run/активацию renewal на новой ноде, не заявляй их успех.

## 5. Права, доказательства и переключение

Обновляй Remnawave через поддерживаемый API, не прямыми SQL UPDATE.
Копируй фактические frontend-права только нужных сквадов, union с текущим
состоянием перед записью; не стирай параллельные добавления. Не выдавай
backend-служебному скваду клиентский frontend-доступ. Не меняй общий профиль
выхода/старые inbounds/привязки прочих нод ради нового маршрута.

Разделяй подготовку и публикацию:

- Кандидат: тест конфигурации установленным Xray, успешный backend для каждого
  запрошенного выхода, hash конфигурации и timestamp доказательств. Перед
  переключением сверь hash и свежесть (разумное короткое окно, например 30 мин;
  время из будущего не принимай). Пустой список проб не является успехом.
- Вооружи проверенный scoped rollback timer до изменения действующей привязки.
  Повторно проверь baseline/ожидаемое состояние. При двусмысленном ответе API
  сначала readback по записанному intent/ID, не повторяй создание вслепую.
- Примени изолированный профиль только к выбранной ноде. Дождись connected и
  listeners; проверь сквады и другие ноды. Не объявляй успех после одного PATCH.
- До публикации: из внешней точки реальный аутентифицированный клиент на новом
  entry/порту должен дать 204 и ожидаемый egress каждого exit. При переносе DNS
  подключайся к новому IP с целевым SNI, не направляй всех клиентов для пробы.
  Проверь legacy с прежними IP/портом/SNI/ключом/short ID/fingerprint.
- Основной и существующий авто-хост сначала проверь как кандидатов с реальными
  параметрами выбранного приложения. Сохрани hidden/remark/order/fingerprint
  и все несвязанные свойства. Общий на несколько нод хост без согласования
  не перепривязывай для всех. Автовыбор проверяй по фактическим маршрутам.
- Только после этих gates публикуй согласованные хосты/параметры подписки.
  При миграции DNS существующего домена переводи его после успешных probes и
  подготовки/публикации нужных привязок, сохраняя старую схему на время TTL.
  Для нового домена предварительный DNS для ACME не считается публикацией VPN.
- Постпубликационная проверка обязательна: получи реальную подписку поддерживаемого
  приложения с нужными User-Agent/HWID/rules; проверь Address/порт/SNI/security/flow,
  основной и авто-маршруты, затем подключись по полученным данным и повтори
  204 + egress. Не выдумывай subscription API; не печатай URL/содержимое/UUID.
  Предпубликационная проба кандидата не заменяет эту проверку.

## 6. Откат, завершение, публикация результата

На провале переключения откати только принадлежащую операции дельту и проверь
возврат рабочего клиента. До отката всех объектов проверь, что их текущие ID,
связи и hashes ещё соответствуют твоему изменению. Сохрани посторонние добавления;
при конфликте останови опасную часть отката и сообщи точный ресурс/причину.
Не восстанавливай целиком старую БД, профиль или firewall поверх чужой работы.
Не удаляй чужие DNS/сертификаты/аккаунты. Не останавливай TLS/туннель, пока на
него ссылается используемая схема. Не уничтожай исходный доступ/443 ради отката.

Маркер успеха записывай только после всех проверок. После ошибки inspect/readback,
а не повторная установка поверх частичного результата; resume проверяет уже
созданное, backup hashes и ownership, не переписывает исходный снимок.

После финальных probes, реальной подписки и применимых TLS/renewal проверок
сними rollback timer. Отдельно проверь inactive timer **и service**, отсутствие
rollback-маркера, неизменность состояния/hashes и работоспособность после снятия.
Произвольный ненулевой exit code systemctl не доказывает inactive: ожидаемый
статус нужно отличать от ошибки; уже выполняющийся rollback нельзя игнорировать.
Удали только собственные временные тестовые аккаунты/процессы и подтверди очистку.

Соблюдай release-процесс текущего проекта, если он есть. Для среды HAM/GIGA с
её действующими правилами: правильный remote/ветка, тесты, опубликованный GitHub
commit до deploy, согласованный один владелец push, проверка финальной синхронизации
и краткий проверенный результат в её журнале. Этот пакет не устанавливает такие
обязательства для чужого VPN и не содержит адресов/credentials инфраструктуры автора.

В отчёте отдели «готово», «не проверено» и «отложено»; назови scope, транспорт,
публичные endpoints, дату сертификата, renewal, клиентские/legacy/подписочные
проверки, backup hash и состояние отката без секретов. Без отдельной пробы из
сети оператора при действующем ограничении не заявляй обход его блокировок.
