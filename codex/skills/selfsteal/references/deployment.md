# Порядок развёртывания

## 1. Инвентаризация без изменений

Проверь Git remote/ветку и реальные доступы. На ноде получи ОС, архитектуру,
IP/маршрут выхода, версии Xray/панели, владельцев портов, firewall, существующий
веб-сервер и сертификаты. SSH — с проверкой host key; при изменившемся ключе
не отключай проверку. Проверяй доступ к DNS через операции зоны: Cloudflare
account-scoped token может не проходить user-token verify, но работать в зоне.
Нужны права Zone Read и DNS Edit только для выбранной зоны либо ручная запись.
Токен/пароли читай из разрешённого секретного файла или используй текущую
авторизованную сессию; не выводи значения и не добавляй их в команду shell,
логи, Git, навыки или публичный журнал. Отключи подробный вывод HTTP-заголовков.

В панели проверь идентичность сервера, активный профиль, все его inbounds,
пользовательские сквады и привязанные хосты, включая скрытый автовыбор.
Из ответов API выводи только выбранные безопасные поля: `rawInbound`, config,
node.configProfile, данные пользователей и docker inspect могут содержать
ключи даже внутри вложенных объектов. Полные снимки сохраняй только в
защищённом каталоге на сервере (root-only), не в рабочем дереве.

Если этот же hostname уже полностью работает, проверь существующее состояние
и продление вместо повторного создания профиля, сертификата и хостов.
Не затирай чужой nginx-конфиг и не занимай уже используемый порт 443.

## 2. Резервирование и подготовка

Сохрани профили, настройки целевой ноды, затронутые хосты/связи сквадов,
конфиги сайта/firewall/контейнеров; проверь читаемость и контрольные суммы.
Снимок делай до первой мутации. Не копируй репозиторную БД или пример env
поверх production. Подготовь ограниченный откат именно этой операции.

Существующий общий профиль никогда не меняй для одной ноды. Создай отдельный
профиль с уникальным именем и глобально уникальными inbound tags, скопировав
конфигурацию и изменяя только целевой inbound и ссылки routing.inboundTag
на переименованный tag. Сохрани остальные inbounds, клиентов, private key,
short IDs, старые SNI, flow, транспорт, sniffing, routing и outbounds. Новые
ключи нужны новой установке, а не миграции рабочих клиентов. Не предполагай
фиксированное количество нод или четыре сквада из примера US3.

Связи новых inbound со сквадами копируй по фактическим старым связям. Старые
inbound не удаляй: они обслуживают другие ноды. Переключай только нужную ноду
и связанные с ней хосты. Если хост относится к нескольким нодам, не меняй его
для всех; согласуй/создай отдельную привязку в рамках выбранной ноды.

## 3. DNS, сайт, сертификат

Повторно прочитай записи выбранного FQDN перед изменением. Создай A DNS only
на подтверждённый входной IP; не путай management IP, NAT/ingress и egress.
Точное существующее соответствие можно использовать. Конфликтующие A, AAAA
или CNAME не перезаписывай. Идентификатор новой записи сохрани для отката.
Проверь API readback и два публичных резолвера; локальный DNS VPN-клиента может
возвращать синтетический адрес. Не считай успешный POST единственной проверкой.

Установи/переиспользуй nginx и ACME-клиент сообразно существующей ОС. Не делай
общего upgrade/restart ноды. Сначала HTTP vhost и проверка challenge, затем
реальный сертификат. Обычно достаточно HTTP-01 с публичным портом 80, без
DNS-токена на ноде. Если порт 80 уже занят, интегрируй challenge в существующий
web-сервис либо согласуй другой способ, а не останавливай его. Сохрани SSH,
ограничения API и firewall. Не отключай firewall целиком.

Сайт — лёгкая статическая одностраничная страница по теме пользователя;
ретро-оформление по умолчанию допустимо, но текст должен читаться на телефоне.
Не придумывай историю бизнеса, отзывы, контакты, реальные заказы и платежи.
TLS vhost слушает только loopback на свободном порту (обычно 8443).
**В контейнере 127.0.0.1 — его собственная сеть**: убедись, что Xray видит
этот target. Host-network и bridge-network требуют разной адресации; не меняй
сеть рабочего контейнера и не открывай локальный TLS в интернет автоматически.

Проверь nginx -t, цепочку и имя сертификата, TLS 1.3 и ALPN h2 через реальный
сетевой namespace Xray. Не используй самоподписанный сертификат/skip-verify
как замену готовому HTTPS. Включи renewal timer и проверяемый reload-hook;
выполни staging dry-run продления (без циклических production ACME-запросов).

## 4. Переключение с контролем

Сохрани базовую проверку старого клиента до переключения. Для теста используй
согласованный технический аккаунт с нужным доступом или временный аккаунт
с коротким сроком и лимитом. Не меняй подписку/платёж/UUID клиента ради пробы.
Запиши intent/UUID до создания временного аккаунта для безопасного восстановления
после неопределённого ответа. Удали только созданный этой операцией аккаунт
после проверки и подтверди отсутствие; действующих пользователей не удаляй.

Для существующей ноды подготовь и проверь ограниченный отложенный откат
профиля/хостов на случай обрыва сессии. Он должен проверять актуальную привязку
и не затирать последующие посторонние изменения. Предупреди о кратком
переподключении только целевой ноды.

В isolated REALITY config: target — доступный локальный TLS listener;
добавь выбранный FQDN в serverNames, сохрани старые значения для кэша клиентов.
Не путай `target` и legacy `dest`; проверь схему текущего Xray и не оставляй
конфликтующих полей. Выполни configuration test самим установленным Xray.
Через API панели сохрани профиль и связи, переключи целевую ноду, дождись
применения. Не обходи API прямыми SQL UPDATE: распределение/кэш нод может
не обновиться. Повторно проверь изменения сквадов перед записью; сохраняй
несвязанные добавления и сообщай о конфликтах.

Сначала проверь VPN-клиентом новые параметры и старый закэшированный вариант.
Затем публикуй домен в Address, Host и SNI целевого хоста и его соответствующего
скрытого автовыбора, сохраняя прочие свойства. В raw/TCP без HTTP-obfuscation
Host обычно не используется; не включай HTTP-obfuscation ради заполнения поля.
Для другого транспорта проверь его семантику, а не копируй raw-настройки.

## 5. Проверки и завершение

- Из внешней точки: правильный обычный HTTPS-сайт через REALITY-порт, доверенная
  цепочка/имя, TLS/ALPN. Просмотр DOM/скриншота — только для проверки сайта.
- Аутентифицированный клиент: HTTPS-запрос с ожидаемым статусом (например 204)
  и подтверждённым ожидаемым egress IP. Egress может отличаться от DNS IP при NAT;
  не считай это ошибкой без сверки с исходной маршрутизацией.
- Для миграции: старые IP/SNI/key/shortId и используемый клиентский fingerprint
  продолжают работать. Дополнительно проверь актуальный распространённый
  fingerprint без смены настройки всем пользователям.
- Реальная подписка поддерживаемого приложения: адрес/порт/SNI/security/flow,
  одиночный хост и автовыбор. Учитывай User-Agent/HWID/rules панели: ответ
  «Приложение не поддерживается» тестовому curl не равен поломке VPN.
  Не печатай URL подписки, UUID клиента или весь конфиг.
- Целевая нода connected, клиенты возвращаются, остальные профили/ноды и
  исходные права не изменены нашей операцией. Дополнительные параллельные
  связи сквадов сохраняй; удаление старых/новых нужных прав — ошибка.
- Продление сертификата проверено, временные аккаунты/процессы убраны,
  отложенный откат отменён и его неактивность подтверждена.

При ошибке после переключения верни предыдущий профиль/привязки и проверь
рабочее подключение. Не останавливай локальный HTTPS, пока REALITY на него
указывает. Откат DNS допускается только для собственной новой записи с теми
же ID/значениями; чужие или изменённые записи не удаляй. Защищённые резервные
копии и неактивный профиль можно оставить для восстановления.

Публикуй только проверенный результат. Если нет пробы из сети российского
оператора при активных БС, так и сообщи; наличие собственного сайта не
доказывает доступность IP/домена в белом списке.
