# Зарубежная нода через российский вход — вручную

Подробная инструкция без нашей вкладки «Инфраструктура». Используем **SSH и обычные разделы Remnawave: профили, ноды, хосты, сквады и пользователи**. Вторая инструкция: [как сделать автовыбор](autovybor.md).

Сверено с кодом нашей инфраструктуры на 19 сентября 2026 года. Это инструкция, а не сообщение о новом развёртывании. Примеры конфигов нужно проверить установленным ядром перед применением.

## 1. Что получится

```text
Happ / Koala → российский сервер:19443 → зарубежная нода:443 → интернет
```

Российская нода принимает TCP и пересылает **тот же поток** зарубежной ноде. VLESS/REALITY, проверка пользователя и выход в интернет остаются на зарубежном сервере. UUID, ключи и SNI зарубежного подключения сохраняются. В клиентском Host меняются только адрес и порт.

Это прозрачный TCP-мост. Он полезен, когда клиенту доступен российский адрес, а российскому серверу доступен зарубежный VPN. Сам по себе он не разблокирует зарубежный IP и не гарантирует обход DPI.

Не путай с другой схемой: российский сервер сам принимает VLESS/REALITY и создаёт отдельное VPN-соединение до выхода. Для неё нужны другие профили и привязки Host. Здесь на RU используется только перенаправление.

## 2. Что подготовить

Нужны **две уже установленные ноды в нашей Remnawave**:

- **RU** — российский сервер, root SSH, нода включена и на связи, профиль отдельный.
- **EXIT** — зарубежный сервер, нода на связи, рабочий клиентский VLESS + REALITY + TCP.

Если сервер пустой, сначала установи Remnawave Node по штатной инструкции установки из своей версии панели, назначь профиль и проверь связь. Этот документ начинается с подключённых нод. Существующую зарубежную ноду переустанавливать не требуется.

Название зарубежного профиля может быть G-CONFIG или другим. Для перенаправления важны его действующие параметры. Уже существующий self-steal сохраняется; новый сайт, домен и сертификат для самого TCP-моста не нужны.

Заполни свою таблицу:

| Обозначение | Что записать |
|---|---|
| `RU_IP` | Публичный IPv4 российского сервера. |
| `EXIT_IP` | Публичный IPv4 зарубежного сервера. |
| `RU_PORT` | Свободный порт RU. Ниже используется `19443`. |
| `EXIT_PORT` | Существующий VPN-порт EXIT. Ниже используется `443`. |
| Host | Обычная зарубежная запись из пользовательской подписки. |
| Профиль RU | Профиль только российского сервера. |
| Профиль и inbound EXIT | Настройки конкретного зарубежного клиентского входа. |

В JSON ниже `203.0.113.20` — **учебный адрес**, обязательно замени его своим EXIT_IP. Реальных ключей и серверных доступов в документе нет.

Три разных порта:

- SSH, обычно `22` — административный вход на сервер;
- Node Port, часто `2222` — связь панели с нодой;
- `19443` — новый порт российского VPN-перенаправления.

Node Port не нужно подставлять вместо VPN-порта.

## 3. Сохрани исходные настройки

До изменений сохрани в закрытой папке:

1. Полный JSON профиля RU — `ru-before.json`.
2. Полный JSON профиля EXIT — `exit-before.json`.
3. Поля Host: Address, Port, профиль, inbound, ноды, SNI, fingerprint, теги и ограничения доступа.
4. Привязки профилей к нодам, активные inbound и доступ сквадов.
5. Тестовую подписку для проверки.

В профилях могут быть приватные REALITY-ключи. Не отправляй эти копии в GitHub и публичный журнал.

Сначала выбери зарубежный Host вручную в клиенте, открой несколько HTTPS-сайтов и запиши внешний IP. Если он заблокирован именно в твоей сети, исходную проверку потребуется выполнить из доступной сети. Открытый TCP-порт сам по себе не подтверждает рабочий VPN.

### Общие профили

Изменение общего профиля будет отправлено всем его нодам. У российского входа должен быть отдельный профиль.

Если профиль RU общий, сначала выдели копию и перенеси привязки именно этого сервера. У скопированных inbound другие идентификаторы: нужно сохранить соответствие активных входов ноды, её Host и прав сквадов. Переименование общего профиля не делает его отдельным. Не назначай пустую копию действующей ноде, не разобрав эти связи.

Зарубежный профиль для самого моста не меняется. Если нужна правка совместимости общего EXIT-профиля, сначала выясни затрагиваемые ноды и согласуй расширение изменения.

## 4. Проверь зарубежный клиентский вход

В обычном разделе профилей открой EXIT и найди inbound, к которому привязан нужный Host. Должны быть:

- `protocol: "vless"`;
- `streamSettings.security: "reality"`;
- TCP-транспорт: `network: "tcp"` или `"raw"` в наших текущих конфигурациях;
- один реальный VPN-порт, например `443`;
- адрес прослушивания, доступный российскому серверу;
- внутри `streamSettings.realitySettings` явно задано `minClientVer: "1.8.2"`;
- fingerprint Host — **firefox**.

Нужная строка внутри существующего `realitySettings`:

```json
"minClientVer": "1.8.2"
```

Это фрагмент, не конфиг для замены. Если настройка уже есть, оставь её. UUID, privateKey, shortIds, serverNames, target, flow и пользователей ради моста не пересоздавай. Проверку сертификатов и REALITY-аутентификацию не отключай.

В нашей прозрачной схеме клиентская REALITY-сессия заканчивается на EXIT. Поэтому совместимость mihomo настраивается там. В схеме с отдельным российским VLESS-входом точка применения была бы другой.

Постоянные изменения делаются **в профиле панели**, а не только внутри контейнера: панель может перезаписать локальный конфиг при обновлении.

## 5. Проверь RU по SSH

На своём компьютере открой терминал:

```bash
ssh -p 22 root@RU_IP
```

Подставь реальный IP и SSH-порт. Пароль вводится по запросу. Следующие команды выполняй **на RU**, не в локальном PowerShell:

```bash
docker ps --format 'table {{.Names}}\t{{.Status}}'
docker exec remnanode xray version
docker inspect -f '{{.HostConfig.NetworkMode}}' remnanode
ss -lntp 'sport = :19443'
```

Здесь `remnanode` — имя контейнера. При другом имени подставляй его.

Ожидается: контейнер работает, Xray выводит версию, сеть контейнера — `host`, порт `19443` свободен. Если сеть другая, отдельно проверь публикацию портов Docker. Не меняй сеть действующего контейнера вслепую.

Если установлен `nc`, проверь с RU зарубежный порт:

```bash
nc -vz -w 5 EXIT_IP 443
```

Замени адрес и порт. Это только TCP-проверка. Полноценное VPN-соединение будет проверено позже, до изменения пользовательского Host.

## 6. Добавь перенаправление в копию российского профиля

Сначала редактируй локальную копию полного RU-профиля. Сохрани прежние настройки и добавь следующие части.

### 6.1. В массив `inbounds`

Добавь объект, заменив учебный IP и при необходимости порты:

```json
{
  "tag": "relay-nl-01",
  "listen": "0.0.0.0",
  "port": 19443,
  "protocol": "dokodemo-door",
  "settings": {
    "address": "203.0.113.20",
    "port": 443,
    "network": "tcp",
    "followRedirect": false
  },
  "sniffing": {"enabled": false}
}
```

`relay-nl-01` — уникальный tag новой пары. Верхний `port` — российский. `settings.address` и `settings.port` — зарубежный VPN. Назначение фиксировано, поэтому sniffing здесь выключен.

Новые REALITY-ключи и список пользователей этому inbound не нужны. Их проверяет зарубежный VLESS.

### 6.2. Найди прямой outbound

В `outbounds` должен быть прямой выход с протоколом `freedom`. Например:

```json
{
  "tag": "direct",
  "protocol": "freedom"
}
```

Если его tag — `DIRECT` или другой, используй фактическое имя с правильным регистром. Если такого выхода нет, добавь отдельный с уникальным tag `relay-direct` и укажи его в следующем правиле. Не меняй первый/default outbound действующего профиля.

### 6.3. В начало массива `routing.rules`

Добавь:

```json
{
  "type": "field",
  "inboundTag": ["relay-nl-01"],
  "outboundTag": "direct"
}
```

При другом имени прямого outbound замени `direct`. Это правило затрагивает только новый inbound. Старые правила остаются ниже.

Если `routing` отсутствует, создай объект с массивом `rules`. Не добавляй второй ключ `routing` рядом с существующим. Между объектами JSON нужны запятые, после последнего объекта запятая не ставится.

### 6.4. Полный пример для отдельной пустой RU-ноды

**Только если у российского сервера нет других клиентов и маршрутов**, полный профиль может выглядеть так:

```json
{
  "log": {"loglevel": "warning"},
  "inbounds": [
    {
      "tag": "relay-nl-01",
      "listen": "0.0.0.0",
      "port": 19443,
      "protocol": "dokodemo-door",
      "settings": {
        "address": "203.0.113.20",
        "port": 443,
        "network": "tcp",
        "followRedirect": false
      },
      "sniffing": {"enabled": false}
    }
  ],
  "outbounds": [
    {"tag": "direct", "protocol": "freedom"}
  ],
  "routing": {
    "rules": [
      {
        "type": "field",
        "inboundTag": ["relay-nl-01"],
        "outboundTag": "direct"
      }
    ]
  }
}
```

Для рабочего российского профиля применяй добавления 6.1–6.3. Замена его целиком этим примером удалит старые маршруты.

## 7. Проверь конфиг установленным Xray

Сохрани подготовленный **полный** профиль как `ru-candidate.json`. Загрузи его через SFTP в `/root/ru-candidate.json` на RU. Затем:

```bash
chmod 600 /root/ru-candidate.json
python3 -m json.tool /root/ru-candidate.json >/dev/null
docker cp /root/ru-candidate.json remnanode:/tmp/ru-candidate.json
docker exec remnanode xray run -test -config /tmp/ru-candidate.json
```

Обе проверки должны завершиться успешно. Первая проверяет JSON, вторая — настройки Xray. Они **не применяют профиль и не запускают второй VPN**.

При ошибке не сохраняй кандидат в панели. Проверь строку ошибки, запятые, ссылки на tag и совместимость параметров. Онлайн-документация Xray уже может называть этот протокол `tunnel` и использовать другие поля. Здесь используется синтаксис `dokodemo-door` нашей установленной реализации; смешивать две схемы нельзя.

## 8. Примени российский профиль и открой порт

1. Убедись, что сохранён `ru-before.json`, а доступ к панели/SSH не зависит от изменяемого VPN.
2. В обычном разделе профилей Remnawave открой профиль RU.
3. Вставь проверенный полный JSON и сохрани.
4. Дождись применения. При необходимости используй штатный перезапуск **только этой российской ноды**.
5. Убедись, что нода снова на связи.
6. По SSH на RU проверь:

```bash
ss -lntp 'sport = :19443'
docker logs --since 2m --tail 80 remnanode
```

Должен появиться слушатель `19443`, без ошибок запуска. Логи могут содержать служебные данные, не публикуй их целиком.

В нашей установленной версии панели служебный inbound без пользователей сохраняется в конфигурации ноды. На другой версии проверь фактический слушатель. Привязывать пользователей или клиентский Host к `dokodemo-door` не нужно.

Во время применения текущие подключения российского сервера могут переподключиться. Зарубежный профиль и общий пользовательский Host на этом шаге остаются прежними.

### Файрвол

Если кабинет провайдера ограничивает входящие подключения, разреши **TCP 19443** на RU.

Если на RU **уже используется активный UFW**:

```bash
ufw status verbose
ufw allow 19443/tcp comment 'relay-nl-01'
```

Если UFW не используется, не включай его поверх другого файрвола: добавь точечное правило в существующий механизм. Не очищай iptables/nftables и не открывай Node Port для всех.

## 9. Проверь путь до изменения подписок пользователей

Создай **отдельную локальную тестовую запись** в клиенте:

1. Возьми рабочее подключение к EXIT из тестовой подписки.
2. Сделай копию с названием `TEST-RU-NL`.
3. В копии измени только **адрес на RU_IP** и **порт на 19443**.
4. Сохрани UUID, SNI, publicKey, shortId, flow и остальные параметры EXIT. Fingerprint — `firefox`.
5. Подключись к копии и открой несколько HTTPS-сайтов.
6. Проверь внешний IP: ожидается зарубежный выход.
7. Повтори в Happ и Koala/mihomo, затем из нужной российской сети.

Если приложение не даёт редактировать подписочную запись, используй отдельный локальный импорт. В VLESS-ссылке меняется адрес и порт после `@`; параметры после `?` сохраняются. Не отправляй личную ссылку в публичный конвертер.

Для теста выбирай конкретный сервер, **не автовыбор**. Иначе приложение может использовать другую ноду.

Если проверка не прошла, общий Host ещё не изменён. Исправь российское дополнение или верни RU-профиль. Не переключай пользователей по одному успешному TCP-пингу.

## 10. Измени обычный Host вручную

После успешной проверки:

1. Открой обычный раздел **«Хосты»**.
2. Найди нужный зарубежный Host из пользовательской подписки.
3. **Address / Адрес** поменяй на `RU_IP`.
4. **Port / Порт** поменяй на `19443`.
5. Сохрани.

Что остаётся:

| Поле | Правильное значение |
|---|---|
| Профиль / inbound Host | Зарубежный профиль и его клиентский VLESS-inbound. |
| Ноды Host | Зарубежная нода. |
| SNI, publicKey, shortId | Прежние параметры зарубежного REALITY. |
| Fingerprint | `firefox`. |
| UUID, название Host, теги и тарифные ограничения | Существующие значения. |

**Адрес самой Node в разделе нод не меняй.** Панель продолжает управлять зарубежным сервером по его настоящему адресу. Российский адрес получает только клиентский Host.

Не создавай вместо него Host на российском `dokodemo-door`: клиентские параметры должны по-прежнему браться из зарубежного VLESS.

Изменение существующего Host затронет всех пользователей, которым он выдаётся, после обновления их подписок. Для изолированного теста используй локальную копию из раздела 9.

## 11. Проверь уже фактическую подписку

1. Обнови подписку в Happ и Koala, отключи и включи VPN.
2. Выбери обычный переключённый Host, а не локальный `TEST-RU-NL`.
3. Проверь полученные адрес RU, порт, SNI, REALITY-параметры и Firefox.
4. В Koala выполни URL-test; затем в обоих клиентах открой несколько HTTPS-страниц подряд.
5. Проверь зарубежный выходной IP.
6. Проверь другой прежний маршрут российского сервера, если он уже обслуживал клиентов.
7. Повтори из сети пользователя в России.

Старая отдельно импортированная VLESS-ссылка сама не обновится. Подписку нужно обновить, отдельную ссылку — заменить актуальной.

Успех из Беларуси или с сервера панели не доказывает доступность у российского оператора. Запиши время, сеть, приложение и результат проверки.

## 12. Возврат напрямую и откат

### Вернуть только прямой маршрут

В том же Host верни сохранённые **исходные Address и Port**. Обнови тестовую подписку и проверь прямое подключение. Затем обнови остальные устройства.

Российское перенаправление можно оставить. Для повторного перехода через РФ достаточно снова проверить его и изменить эти два поля Host.

### Убрать российское дополнение

После возврата Host и проверки прямого пути:

1. Убедись, что больше не нужны старые кешированные подключения к российскому порту.
2. Удали из RU-профиля только inbound `relay-nl-01` и его правило.
3. Если добавлялся отдельный `relay-direct`, удали его только при отсутствии других ссылок.
4. Проверь полный JSON ядром и примени через панель.
5. Удали только правило порта, добавленное этой операцией.

Для UFW, если это правило создавалось выше:

```bash
ufw delete allow 19443/tcp
```

Не восстанавливай целый старый профиль поверх чужих последующих изменений. `ru-before.json` подходит для полного возврата только если после твоей операции профиль больше никто не менял; иначе убирай лишь свои дополнения.

**Здесь нет автоматического отката нашей вкладки.** Ручной способ требует независимого доступа к панели и SSH. Поэтому сначала готовится и проверяется путь, и лишь затем меняется пользовательский Host.

## 13. Несколько зарубежных нод через один RU

Каждому выходу — свой порт и tag:

| Пара | Порт RU | Tag | Куда передавать |
|---|---|---|---|
| Нидерланды | `19443` | `relay-nl-01` | IP первой ноды и её VPN-порт |
| Германия | `19444` | `relay-de-01` | IP второй ноды и её VPN-порт |

Для каждой пары добавь отдельный inbound и правило. Один российский IP допустим у нескольких Host; порты должны соответствовать нужным выходам. Проверяй каждую пару отдельно и сохраняй предыдущие маршруты.

## 14. Разбор ошибок

| Симптом | Что проверить |
|---|---|
| На RU нет слушателя | Нужный профиль, применение, занятость порта, результат Xray-проверки, сеть Docker. |
| Слушатель есть, снаружи таймаут | Файрвол ОС/провайдера, доступность RU_IP и порта из сети пользователя. |
| TCP есть, сайты не работают | EXIT_IP/порт, UUID/SNI/publicKey/shortId, реальное прохождение VPN между серверами. |
| Выходной IP российский | Другое правило или другой выбранный сервер. В этой схеме ожидается EXIT. |
| Happ работает, Koala нет | Фактический Mihomo-конфиг, Firefox и `minClientVer` клиентского REALITY-inbound на EXIT. |
| Тестовая запись работает, подписка нет | Address/Port и привязки Host, обновление подписки, выбранный профиль приложения. |
| Наш переключатель после ручной правки выдаёт предупреждение | Он хранит прежнее состояние. Перед его дальнейшим использованием нужна сверка ручных изменений. |

### Если не работает участок RU → EXIT

Может понадобиться другой межсерверный транспорт, например reverse SSH: зарубежный сервер устанавливает туннель к российскому, и российский Xray использует локальный порт этого туннеля.

Это отдельная настройка: ограниченная учётка, ключ, проверенный SSH host key, сервис восстановления и loopback-порты. Замена EXIT_IP на `127.0.0.1` без созданного туннеля не поможет. Эта инструкция описывает прямой TCP-мост и не устанавливает reverse SSH.

## 15. Автовыбор и технические источники

Если обычный Host уже входит в пул, после обновления подписки его российский адрес попадёт в сгенерированный автовыбор. Скрытый дубль не нужен. Добавление новой ноды в пул описано в [autovybor.md](autovybor.md).

Конфигурация сверена с `orchestrator/app/gconfig_model.py` нашей инфраструктуры. Общий принцип перенаправления описан в [Xray Tunnel/dokodemo-door](https://xtls.github.io/en/config/inbounds/tunnel.html), выбор выхода по inboundTag — в [Xray Routing](https://xtls.github.io/en/config/routing.html). Онлайн-документация может опережать установленное ядро; проверяй свой полный конфиг через `xray run -test`.

Полный учебный JSON из раздела 6.4 прошёл проверку конфигурации Xray 26.7.28 в отдельном контейнере без сети. Это проверка синтаксиса и параметров примера, не проверка связи между твоими серверами.
