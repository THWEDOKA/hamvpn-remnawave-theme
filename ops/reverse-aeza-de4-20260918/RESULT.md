Настройка выполнена по явно выбранному владельцем reverse-ssh-reality workflow.

## Итоговая схема

- Клиентский хост `🇩🇪 Германия - 4`: `193.233.222.244:18446`.
  SNI `in-de4.torcalc.ru`, Firefox, UUID, REALITY-ключи, short ID и Vision
  клиентского подключения сохранены. Сам Host и скрытый `ABP-42-DE-HIDDEN`
  не изменялись; состав автоподбора не менялся.
- ENTRY: `AEZA-MOST #633`, `193.233.222.244`.
  Только outbound `exit-de94` переключён на новый служебный VLESS/REALITY
  через `127.0.0.1:34443`. Остальные inbounds/outbounds/routing сохранены.
- EXIT: `62.60.226.94`. Добавлен отдельный backend
  `127.0.0.1:30443`, VLESS/REALITY/Vision, self-steal target
  `127.0.0.1:8443`, SNI `de94.torcalc.ru`.
  Старые публичные TLS/Hysteria inbounds на 443 сохранены.
- Германия инициирует **OpenSSH `-R`** на Aeza. Отдельный persistent unit
  `ham-rs633-de4.service`, отдельная непривилегированная учётка на каждой стороне.
  SSH private key создан и остаётся только на EXIT; на ENTRY передан public key.
- На ENTRY отдельный Match User: public-key only, remote-only, точный listener,
  запрет shell/exec/PTY/agent/X11/local/dynamic/streamlocal. Effective policy
  root и существующих ham-учёток проверена неизменной.
- Client config/known_hosts/unit root-owned. Host key ENTRY закреплён через
  уже доверенный административный SSH-канал. Process на EXIT не root.
  IP sandbox systemd подтверждён реальными ingress/egress BPF attachments.
  PermitListen ограничивает listener, а фиксированный target задаётся
  root-owned client config, не самим PermitListen.
- Новый служебный сквад имеет только backend-права, без frontend-доступа.

Старый Paramiko-туннель **только на Германии — 4**
(`ham-entry244-reverse.service`) остановлен и disabled после успешной миграции.
Файлы и прежние реквизиты оставлены для контролируемого восстановления.
Его listener 24443 на ENTRY отсутствует; соседние 21443/22443/23443 сохранены.

## Проверки

- Кандидаты проверены установленными ядрами: ENTRY Xray 26.7.28,
  EXIT Xray 26.3.27. Модели и scoped rollback покрыты пятью offline-тестами.
- Из реального host namespace ENTRY новый backend дважды дал:
  три HTTPS 204, egress `62.60.226.94`, HTTPS download 3 145 728 байт.
  Между пробами перезапускался **только новый tunnel unit**.
- После переключения проверены реальные экспортированные параметры Happ/Xray
  обычного хоста и его отдельного участника автоподбора: оба прошли
  три 204, ожидаемый IP, загрузку 3 МиБ. Это не принудительный выбор Германии
  всем общим autoselect-балансировщиком.
- Отдельный Windows mihomo с настоящей свежей mihomo-подпиской:
  Firefox, HTTP 204, `62.60.226.94`, 3 МиБ. Работающий HamVPN PC, TUN,
  системный прокси и пользовательские настройки не менялись.
- После снятия rollback timer и остановки старого туннеля повторены реальные
  пробы main/auto-member с тремя 204, egress и 3 МиБ — успешно.
- Timer **и service** отката inactive, jobs отсутствуют, rollback-маркера нет.
  Тестовый пользователь удалён; отсутствие подтверждено read-only SQL.
- Новый unit active/enabled, non-root, финальный `NRestarts=0`.
  R/B слушают исключительно `127.0.0.1`; профили/права/Hosts сверены ещё раз.

## Исходные сбои соседей и границы вывода

До изменений серверные probes имели ошибки на всех четырёх маршрутах:
часть 204 проходила, но полный набор не проходил. После миграции Польша
прошла контрольные 204/IP, Германия — 3 продолжила timeout, Нидерланды
дали 204, но IP-запрос завершился ошибкой. Их настройки и туннели не менялись.
Это не отчёт об исправлении соседей, не доказательство причины их сбоев
и не гарантия отсутствия кратких сетевых пауз.

Телефон владельца в его сети ещё должен подтвердить результат. Обновлять
подписку из-за этой миграции не требуется: клиентские параметры сохранены.
После одного применённого варианта дальнейшие варианты без ответа владельца
не разворачивать. Keepalive/restart восстанавливают туннель, но не оборванные
TCP-сеансы; скорость и доступность у всех операторов не гарантируются.
